總覽一條九步嘅流水線

由頭到尾，冇一步係「叫 AI 睇下」。每一步都係人手寫嘅規則， 每一條規則都可以指返出邊行 code、點解要咁寫。

諗住你收到一疊紙，唔識睇。你要做九件事：

睇下係咩紙 → 讀出面啲字 → 記住邊個字排喺邊 → 分開邊度係一段話、邊度係一個表 → 搵「名：答案」呢啲對 → 執返啲讀錯咗嘅名 → 同旁邊嗰份靚啲嘅紙對一對 → 用眼睇下有冇人簽過名同蓋過印 → 最後抄落一張整齊嘅表度。

最緊要明白一件事：PDF 入面根本冇「欄位」呢樣嘢。 PDF 只係記住「呢串字，畫喺 x=72、y=708 呢個位，字體 10pt」。 「Contract Number」同「C159040」對電腦嚟講只係兩堆各自畫喺某個座標嘅字母， 之間冇任何關係。

所以第 ③ 步先係全條線最重要：由一堆座標，重新砌返出「呢兩堆字係同一行」、 「呢一行入面有三格」、「呢三格對齊咗上面嗰行嘅三格，所以佢哋係一個表」。 之後步驟做嘅嘢，全部建基喺呢個還原出嚟嘅排版上面。

①認檔案 extFor · parseByExt Tier 0

好似郵差咁：拎起封嘢先睇下係信、係相、定係一本簿， 然後放去唔同嘅籃仔，因為開唔同嘅嘢要用唔同嘅方法。

第一步唔係讀內容，係決定用邊條路去讀。判斷次序好明確：

  1. 檔名優先。檔名尾如果有副檔名（1–8 個英數字），就用佢，唔會再問 MIME。
  2. 檔名完全冇副檔名嗰陣，先至查 MIME type。

點解檔名贏？因為寄件人成日標錯—— demo 電郵入面就有個 .mht 附件被標成 application/octet-stream。而檔名係寄件人同用戶真係見到嗰樣嘢。

MIME 後備亦都補返一個真實 bug：PostalMime 遇到冇檔名嘅附件會派個 attachment_3 做佔位名，嗰個尾巴嘅點就係佢成個名。

認完之後就分五條路：

  • PDF → 睇下有冇文字層；有就直接讀，冇就自動跌落 OCR。
  • 圖片（png / jpg / gif / bmp / tiff / webp）→ 一定行 OCR。
  • Excel / CSV → 直接讀，完全唔使 OCR——本身已經係結構化資料。
  • 電郵（.msg / .eml / .mht）→ 讀信本身， 再逐個附件遞迴行返成條流水線。
  • 其他 → 明講「唔支援」，唔會扮讀到。

電郵入面嘅附件會再入返呢個決策樹一次（depth + 1）， 所以信入面嘅 PDF、圖、Excel 全部照讀。

但係「容器」唔准套娃。

.msg 同 .eml 只喺 depth 0（即用戶自己揀嗰個檔）先會拆； .mht 放寬到 depth ≤1（可以坐喺一封信入面，但唔可以再落一層）。

所以一封信夾住另一封 .eml，入面嗰封唔會被拆開—— 佢會被報做「唔支援，已跳過」，但個檔本身仲喺度、下載得。

呢個係刻意嘅：容器唔肯嵌套，就冇可能無限遞迴。 代價係一封轉寄嘅信要人手拆一層，換返嚟嘅係冇一個惡意或者手殘嘅 .eml 可以令個 tab 死。

  • previewKindFor(ext) — 行 2882。決定 App 用邊種 viewer 去顯示。

時間預算

成個 engine 喺瀏覽器 main thread 上面行，所以每一步都要肯放手：

  • 軟死線 ATTACHMENT_OCR_BUDGET_MS = 420000（7 分鐘）— OCR 嘅上限。到期就停喺當前嗰頁，保留已經讀到嘅嘢，並標 truncated: true。 真正決定一個附件可以用幾耐嘅係佢。
  • 硬 timeout ATTACHMENT_TIMEOUT_MS = 軟死線 + 150000（9.5 分鐘）— withTimeout 直接 reject，已經讀到嘅嘢全部丟埋。 呢個係防「一個爛 PDF 永遠唔 resolve，卡死後面每一個附件」。
  • withTimeout(promise, ms) 行 2918、yieldToUi() 行 2932 — 後者係一句 await，純粹畀瀏覽器抖一抖去重繪，唔係咁個頁面會凍住。
  • MANY_ATTACHMENTS_THRESHOLD = 10 行 2893 — 超過就先出一句 「⚠ 有 N 個附件，可能要等陣」。純資訊，唔會擋、唔會封頂。

兩個死線之間嗰 150 秒唔係隨手加嘅，係「一版慢頁」。

軟死線只會喺頁與頁之間檢查，所以死線到嗰刻仲喺度行緊嗰一頁， 點都要行完先停得。如果嗰次超時剛好撞穿硬 timeout， 咁軟死線辛辛苦苦保住嘅半份結果，一樣會被丟晒—— 軟死線就白設。

所以個 gap 要闊到夠一版最慢嘅頁行完：一版全版 A4 掃描， 喺 laptop 上面差唔多要兩分鐘。

順帶一提，硬 timeout 曾經係 45 秒， 結果一份真實嘅已簽署合約成份被丟掉——OCR 本身就係要一兩分鐘嘅。

附件係先攞 bytes、再解析，而且攞 bytes 嗰步喺 withTimeout 外面 （行 3048 附近嘅註解講得好白）。解碼好快，解析先會 hang。 咁樣排次序，即使一個 PDF 永遠 render 唔完，用戶都仲可以喺 App 度睇同下載返個附件。

②攞字：文字層定 OCR pdf.js · PaddleOCR Tier 3

A. 有文字層嘅 PDF：啲字本身已經喺入面

有啲 PDF 好似一本打好字嘅書——啲字係真係「字」，可以 copy 得。 咁就唔使認，直接攞得。

由 Word、Excel 印出嚟嘅 PDF，入面藏住每個字嘅原文同位置。 pdf.js 交返嚟嘅唔係一頁文字，而係一堆碎片，每一片有：

  • str — 嗰段字本身（可能只係「Contract」四個字，甚至一兩個字母）
  • transform[4] / transform[5] — 佢畫喺頁面邊個 x / y
  • width — 佢佔幾闊
  • transform[0] — 字體大細

⚠ PDF 嘅 y 軸係向上嘅：y 越大代表越近頁頂。所以排序係由大到細。

呢啲碎片本身冇「行」、冇「格」、冇「表格」嘅概念。全部要靠第 ③ 步砌返出嚟。

groupItemsIntoLines(items) 行 1051 收嘅就係 pdf.js 嘅 textContent.items。第 1062 行嘅 clusters.sort((a, b) => b.y - a.y) 就係「PDF space is y-up」嘅補償。

B. 掃描件同相：要用 OCR 認字

影相影返嚟嘅文件，對電腦嚟講只係一堆黑黑白白嘅點，同一張貓相冇分別。 OCR 就係一個學過好多字嘅細路，望住啲點，逐個估：「呢個係 A」、「呢個係 8」， 同埋話返你聽佢有幾肯定。

用嘅係 PaddleOCR（PP-OCRv6 細模型），透過 onnxruntime-web 喺你部機嘅瀏覽器入面行，識英文同中文。

文件本身永遠唔會離開你部電腦。唯一會用到網絡嘅係第一次行 OCR 嗰陣 由 CDN 攞大約 30 MB 嘅辨識模型，攞完就 cache 住。 之後就算完全冇網絡都照行。

（唯一例外係你自己撳「Smart extract」——嗰粒掣會將文件送去 Gemini， 而佢係一粒你要親手撳嘅掣，唔會自動行。）

OCR 交返嚟嘅每一舊嘢有三樣：一個四角框、認到嘅文字、 同埋一個 0 到 1 之間嘅信心值。 Engine 跟住將呢啲框轉返做「行 + 格」，再交同一個 buildBlocks 去分區——呢個就係成個 engine 最關鍵嘅接駁位。

做法：每個框取中線，同上一行嘅中線相差喺「字高中位數 × 0.6」之內就當同一行； 行內按 x 排序；每個框自己就係一格。

  • OCR_MODEL 行 827 — PpuPaddleOcr.V6_SMALL_MODEL， 喺 Node 底下（冇呢個 global）會係 null，所以 engine 照 load 得到去做純函數測試。
  • ocrResultsToLines(results) 行 847 — 同一行容忍 medH * 0.6（行 866）；大間隔 > max(medGap*1.7, medGap + medH*0.8)（行 884）。

OCR 路同 PDF 路唔係「一模一樣嘅 shape」——差三個 key， 而呢三個 key 各自靜靜雞閂咗一個功能。

groupItemsIntoLines 出 { text, cells, cellStarts, cellParts, yGapBefore, gapRatio, bigGapBefore }； ocrResultsToLines 只出 { text, cells, cellStarts, bigGapBefore }。 少咗 cellParts、yGapBefore、gapRatio。

C. 打橫、倒轉嘅掃描

本書擺歪咗，你會擰個頭去睇。部機做嘅嘢一樣， 不過佢係「擰四次，邊次睇得最清楚就用邊次」。

掃描件成日打橫或者倒轉。做法係：

  1. 先縮細張圖（長邊 1000 px）試讀一次——快、平。
  2. 如果平均信心值低過 0.7，就順住 180° → 90° → 270° 再試。 180° 排第一，因為倒轉係最常見、亦最平排除嘅一種。
  3. 比較四個方向唔係比信心值，係比一個分數： 信心值 × √(認到幾多個字)。
  4. 方向一份文件只判斷一次，之後嗰幾十頁直接沿用—— 唔會每頁都試四次。
常數值意思調大／調細會點
OCR_GOOD_CONFIDENCE0.7 低過呢個平均信心就試轉方向 調高：正方向嘅頁都會白試三次，慢四倍。調低：真係倒轉嘅頁唔會重試，成頁變垃圾。
OCR_PROBE_LONG_EDGE1000 試方向嗰次嘅解像度（長邊 px） 試探用低解像度先抵——只係要比較四個方向邊個高分，唔係要讀得準。
OCR_ROTATION_RETRY_ORDER[180,90,270] 重試次序 180 行先係因為倒轉最常見；命中就慳返兩次。
OCR_TARGET_LONG_EDGE2200 真正 OCR 嗰次嘅目標解像度 細過呢個，細字會糊到認唔到；大過就白燒時間同記憶體。
OCR_MIN_SCALE1.5 最少放大幾多倍 本身已經好大張嘅頁都至少放大 1.5×，因為 PDF 預設 render 尺寸對 OCR 嚟講太細。
OCR_MAX_SCALE4 最多放大幾多倍 封頂，唔係一張細相會 render 成幾萬 px、爆記憶體。

ocrRenderScale(page, targetLongEdge) 行 987 就係計呢個倍數， 並且同一個函數亦畀墨水偵測（第 ⑧ 步）用嚟 render 細張版本。

點解要重試而唔係一開始就試四個方向？ 因為 OCR 係全條線最慢嘅一步。九成掃描件都係正嘅， 用一次低解像度嘅平試探換返「唔使無端端做四倍功夫」，係抵嘅。

點解個分數要乘 √字數？ 淨計信心值嘅話，一版「好肯定咁認到三個字」會贏過 「好好咁認到四百個字」。所以要計埋讀到幾多。 但又唔可以直接乘字數——咁一版理直氣壯嘅亂碼會靠量取勝， 所以開方壓一壓。

呢個分數只會攞嚟比同一頁嘅四個方向，佢嘅絕對值冇任何意義。

兩個踩過先知嘅位（runOcrOriented，行 939）：

一、比較要公平。試方向嗰陣，連「唔轉」嗰個都要重新用細張版本再讀一次先好攞去比。 原本攞「全解像度嘅正方向分數」去同「縮細咗嘅三個轉向分數」比，正方向次次都贏—— 等於根本冇試過。

二、認唔到方向唔算數。如果某一頁因為冇時間而跳過咗試探， 個 memo 會留空，等後面有時間嘅頁再試。 如果亂咁記低咗「呢份文件係正嘅」，成份掃描件就冇得返轉頭。

③還原排版：由座標砌返「行 / 格 / 欄」 groupItemsIntoLines · lineItemsToCellsAndText · clusterColumnStarts Tier 3

想像成頁字全部俾人剪爛咗，變咗一堆紙碎， 每張紙碎背面寫住「我本來喺左邊 7 厘米、上面 3 厘米」。 你要做嘅係：高度差唔多嘅擺埋一齊做一行 → 一行入面隔得遠嘅分開做一格 → 再睇下每行嘅格係咪都對齊晒喺同幾個位，係嘅話就係一個表。

呢一步分四個動作，每個都只係做一件好細嘅事，但錯一個成頁就散。

1 · 邊啲碎片係同一行

y 座標相差喺 2.5 點之內就當同一行。用容忍值而唔係「完全相等」， 係因為同一行入面唔同字體大細嘅字，基線會差少少。

之後計成頁行距嘅中位數。某一行同上面嗰行嘅距離，如果大過 「中位數 × 1.7」或者「中位數 + 6」（邊個大用邊個），就標佢 bigGapBefore——即係「呢度開始係新一舊嘢」。

中位數會封頂喺 20。因為一頁得幾行字嘅時候中位數會爆大， 咁就會將「標題 + 表格 + 總數」三舊完全唔同嘅嘢黐埋做一舊。

2 · 一行入面點分格

由左掃到右，見到兩段字之間隔咗大過「10 點」或者「字體大細 × 2」（邊個大用邊個）， 就當中間有一條睇唔到嘅間隔線，切開做兩格。

切完之後，每一格記低三樣嘢：格入面嘅字、格由邊個 x 開始、 同埋格入面每個字碎自己嘅 x。第三樣好似多餘，但係後面救命—— 見下面「兩欄黐埋」。

3 · 邊幾個 x 其實係同一欄

將成個區域所有格嘅起點 x 掉埋一齊，相差 22 點以內嘅埋堆， 每堆取平均值。呢啲平均值就係呢個區域「隱形嘅欄位線」。

一份文件從來冇話畀你聽佢有幾多欄，係由好多行嘅起點自己聚出嚟嘅。

4 · 一行摺咗兩行，要黐返

窄嘅表格欄會將內容摺落下一行。判斷條件好嚴：

  • 成個區域要有兩種明顯唔同嘅行距（緊嘅摺行距、鬆嘅換行距）。 如果行距全部一樣，即係每行都係獨立一行，唔准黐。
  • 下面嗰行嘅行距要喺「最緊行距 × 1.25」之內。
  • 下面嗰行每一格都要落喺上面嗰行已有嘅欄上（±14）。
  • 而且下面嗰行只可以碰到一欄。碰到兩欄或以上就係新一行記錄， 唔係摺行——唔係咁連續幾行表格會一路黐落去變一嚿。

  • 唔可以淨係數字、貨幣符號、括號（$1,234.00 唔係標籤）

值摺咗落下一行點算？

⑧睇墨水：簽名同公司印 analyzeInkImage · findSignatures · findChops Tier 1

一份簽咗名嘅合約，同一份未簽嘅合約，啲字係一模一樣嘅。 所以就算讀得幾好都分唔到。

唯一嘅分別係手寫嘅墨水。所以呢一步唔再讀字，直接望張相：

簽名 = 一劃好大、好長、入面空空哋嘅嘢，比周圍啲字大好多。
印章 = 一個閉合嘅圈，通常紅色或者藍色，中間困住啲字。

三個觀察撐起成個偵測器：

  1. 印刷字係成千上萬粒細細粒、而且大細好平均嘅墨點。
  2. 簽名係一劃好大嘅嘢，比任何一個印刷字大幾倍， 而且喺自己個框入面空得好緊要。
  3. 印章係有顏色嘅，而喺一份商業文件上面， 幾乎冇第二樣嘢係有顏色。

一 · 先搞清楚咩係「白紙」

唔可以假設白色 = 255。一張灰濛濛嘅影印本，佢嘅「白」可能只係 0.75。 所以先數一數成頁嘅光暗分佈，攞第 90 個百分位做「紙」—— 用高百分位而唔係最光嗰點，係因為一粒白色雜訊或者一嚿過曝就會搞亂晒。

然後：暗過「紙 × 0.78」嘅就算墨水。

二 · 分兩層

  • 深色層——所有夠暗嘅像素。簽名喺呢層。
  • 顏色層——飽和度 ≥ 0.30 嘅像素。印章喺呢層。 門檻唔可以太低，唔係黑字邊緣嘅 JPEG 彩邊都會當咗顏色。

紅色band：色相 ≤25° 或者 ≥315°。藍色band：195°–315°。 綠同黃故意剔除——嗰啲係螢光筆同信頭裝飾。

紅色 band 特登拉返去 315°，等洋紅都算「暖色」。 因為信頭上面嗰個洋紅色 logo，係全張紙唯一一件形狀似到手寫嘅嘢， 兩個 band 之間留條罅就會俾佢扮成「冇顏色」溜咗入去。

「印刷字」點認？——睇基線。

印刷字全部企喺同一條基線上，而且大細差唔多；手寫兩樣都唔係。 所以：一組如果由 6 嚿或以上組成， 而且佢哋嘅底邊標準差 ≤ 組高 × 0.16、 高度標準差 ≤ 平均高 × 0.28——咁就係一個印刷字（實際上係個大標題， 因為得大標題先夠大過到上面啲尺寸關）。

點解係 6 唔係 4？因為一個斷成四五筆嘅真簽名， 有機會啱啱好排得幾整齊；而呢度就真係有兩份簽咗名嘅文件係咁。 一個印刷標題嘅字母梗係多過五個。

PDF 自己講嘅嘢，勝過任何啟發法。

有文字層嘅 PDF 已經精確講咗每個打字字元喺邊。 坐喺嗰啲位置上面嘅墨水，按文件自己嘅講法就係印刷字——唔使估。

呢個就係點解一份未簽嘅報價單上面， 空白簽名線下面印住嘅「Authorised Signature」唔會被報做簽名。

做法：將文字位置畫落一個 8×8 像素嘅粗格上， 一嚿嘢如果超過 60% 嘅格都係文字格，就剔走。 掃描件冇文字層，就只可以靠形狀。

五 · 點認一個公司印

印章之所以係印章，係佢個外框：一個連續嘅圈、橢圓或者圓角方框， 將入面啲字困住。

最關鍵嗰個測試叫 largestHoleRatio： 由框嘅四條邊灌水入去，睇下有幾多張紙係灌唔到嘅。 灌唔到嘅就係被墨水困住嘅「窿」。

呢個係一個拓撲測試，唔係形狀比例——所以圓形、橢圓、方形嘅印都過到， 而任何形狀比例都做唔到呢件事。

簽名再點龍飛鳳舞都好，你永遠可以由紙邊行入去；一個閉合嘅印就唔得。

技術細節：紙用 4 方向灌、墨用 8 方向連。 倒轉用嘅話，背景會由一像素幼嘅筆劃嘅對角線罅走甩， 結果每個圈都會讀成係開口嘅。

其餘關卡：短邊 ≥「頁長邊 × 0.025」同「字高 × 3.5」兩者較大者 （下限故意低，因為呢度真係有 40 像素咁細嘅簽名章）； 長邊 ≤ 頁長邊 × 0.35；長闊比 0.30–3.2； fill 0.02–0.55（超過就係實心 logo）； solidity ≤ 0.75（超過就係實心形狀，唔係外框）； ruleRatio ≤ 0.55（超過就係有色表格邊框）； 窿 ≥ 0.15。

同一嚿嘢會喺兩層各問一次：顏色層可以喺蓋住印刷字嘅情況下乾淨咁攞到紅印； 但一份影印本／灰階掃描根本冇顏色，嗰度個印只可以喺深色層度生存。

  • 同一種標記重疊超過 0.5 → 當一個。
  • 唔同種要重疊到 0.85 先當一個—— 因為「印蓋喺簽名上面」喺呢度係正常簽約方式，兩者本來就重疊。 太快合併就會答到「有印」但同時失去「有簽名」。
  • 一頁最多報 6 個標記。
  • 如果一頁搵到超過 6 個簽名——嗰個唔係簽咗六次， 嗰個係一張圖、一幅地圖或者一張相片。所有簽名結果全部丟棄， 只留印章。誠實講「冇」好過亂報。

七 · 邊幾頁值得睇

望一頁要 render 一次再掃晒每粒像素，好貴。所以：

  • 文件 ≤8 頁 → 全部睇。
  • 長過 8 頁 → 揀「內容提過簽署」嘅頁（一條中英對照嘅正則： authorised signature、for and on behalf of、 company chop、簽署、蓋章…） 加埋最後 3 頁，最多 8 頁。
  • 睇嘅次序都特登排過：提過簽署嘅頁行先。 因為有啲表格範本一頁要幾秒先畫得完， 25 秒嘅預算可能中途就用完——由頭到尾咁睇， 就啱啱好將預算花喺最唔可能有簽名嗰啲頁度。

「未睇過」同「睇過冇嘢」係兩件事，永遠唔准溝埋。

睇過而冇嘢 → marks = [] → 報 Not found。
未睇過 → marks 保持 undefined → 唔會當佢乾淨。
有頁未睇過 → 報 Not found on the pages checked。

連 render 失敗都係 resolve(null) 而唔係空陣列—— 一個空陣列等於聲稱「我望過」。

⑨ATQ：一張表變成逐項記錄 parseAtqWorkbook · parseAtqCostTable · dedupeAtqRecords Tier 1

ATQ 係一張「批准報價單」。一張表上面可能買咗四樣嘢。

後面啲人要嘅唔係「一張表」，係四張獨立嘅小卡， 每張寫住一樣嘢買咩、幾錢、邊間供應商。

麻煩位喺：同一張表成日寄咗兩次——一次係 Excel、一次係印咗做 PDF。 如果兩次都數，四樣嘢就會變咗八樣。

兩條路，一個形狀

ATQ 可以用兩個樣入嚟，兩條路刻意整到出一模一樣嘅記錄形狀， 等下游冇一個地方需要理封信入面帶咗邊個版本：

  • Excel 版（parseAtqWorkbook）—— 要有 Cost 同 ATQ 兩張工作表先出手。 Cost 每行一件貨；ATQ 係一柱「A 欄標籤、B 欄值」， 載住成張表共用嘅資料（客戶名、合約編號、起訖日…）， merge 落每一件貨度。
  • PDF 版（parseAtqCostTable）——由印出嚟嘅成本表度讀返同一啲欄。

PDF 版嘅三個難位

  1. 標題橫跨三行。一隻字落喺三行嘅邊一行， 會隨住上面嗰段字有幾長而變。所以欄位唔可以靠位置認， 要將第一件貨之前所有行嘅同一欄直向黐埋一齊再認。
  2. 一件貨可以佔幾行。每欄各自摺行， 所以帶住項號嗰行只有每格嘅第一行，下面幾行係續集。 唯一嘅標記就係項號嗰格係空嘅。
  3. 續集唔一定用空格接。對住同一張 ATQ 嘅 Excel 版逐格核對過 （唯一嘅 ground truth），全 corpus 有三種情況： 參考編號後面跟描述、描述斷喺半個 token、工單清單以逗號起行。 規則：如果斷點本身已經有標點（左邊以 - 結尾， 或者右邊以 ,.;:) 開頭），就唔加空格—— 呢一條就完全重現到三種情況。

另外，一個參考編號係一個唔會斷開嘅 token。 所以「全部係英數 + 空格」形狀嘅參考值，會將空格全部剷走—— 嗰啲空格係欄位摺行整出嚟嘅，唔係內容。

四條 key 嘅守衛。一張表冇齊 itemNo、productType、vendor、 totalValueOfQuotation 呢四個欄，就唔係成本表， 無論佢似成點都好。

呢條守衛炸過一次：某張 ATQ 將 Total Direct Variable Cost with HKT (HKD): 印咗喺標題第一行嘅同一條物理線上，摺完之後成句嘢黐咗喺 ITEM NO. 前面 → itemNo 認唔到 → 四條 key 唔齊 → 成張表所有項目消失。

修法係將正則由「只錨頭」改成「錨頭或者錨尾」 （/^itemno|itemno$/）——因為上面漏落嚟嘅字， 永遠係以前綴形式出現。

撞埋一齊嗰陣：8 件 vs 4 件

呢個係成個 codebase 最好嘅教材。

atqRecordsFromTables 加入去，係為咗令 PDF 版 ATQ 出到同 Excel 版一樣嘅記錄。合理。

但每一封 demo 電郵都同時帶住兩個版本， 而合併嗰句係 records = records.concat(owned)。 結果一張只有 4 件貨嘅 Cost 表，App 報「呢張 ATQ 涵蓋 8 件」。 成個 corpus 由 12 件真嘢變咗 32 件——而呢個膨脹當時仲被當成係戰績報上去。

教訓寫成咗規矩：

  • 加任何一條會發出 fields 或者 records、 而現有路徑已經處理緊嗰類文件嘅新路徑之前， 先寫低「兩條路一齊開火會點」，再去 corpus 搵一份會同時觸發兩條嘅文件。 喺呢度，兩條一齊開火係常態，唔係邊緣情況。
  • 兩條都會開火嘅時候，要加身份鍵嘅係合併點，唔係任何一邊嘅生產者。
  • 而且——兩個來源覆蓋唔同嘅欄，唔代表要讓弱嗰個贏去保覆蓋率。 先查權威來源係咪真係有嗰啲資料。今次真係有： Cost 表本身就有齊十一欄， 係當時嗰個 COST_COLUMN_MAP（精確字串表， 已經換成而家嘅 ATQ_COST_COLUMNS 正則表）只讀咗五欄。

去重規則

  • 身份鍵 = ATQ 參考編號。先睇記錄自己嘅 ATQ Ref. No. 欄； 冇就由來源檔名度用 ATQ-\d{6}-\d{5}-V\d{2} 抽（PDF 版唔一定印個編號做欄位， 但兩個附件都係用個編號嚟命名嘅）。
  • 同一個編號嘅一組入面，只要有 Excel 記錄，就丟走所有 PDF 記錄。
  • 認唔出係邊張 ATQ 嘅記錄，兩邊都一律保留。

點解 Excel 贏？因為佢係導出源頭——值準確、冇 OCR、冇版面推斷。 仲有：當一次請求只covered ATQ 其中幾件貨， Excel 本身已經被收窄咗（「(Item 2).xlsx」對住一份成張表嘅已批 PDF）， 攞 PDF 就會加返呢張請求根本唔包嘅貨。

A. 試算表：本身已經係結構化資料

Excel 唔使認字——每一格喺邊本身就寫得清清楚楚。 所以連 OCR 都唔使開。

問題唔係「點讀」，係「邊啲格係填表、邊啲格係一張清單」。

因為冇呢個判斷，一張資料表嘅標題行會出到 「Product Number = Product Description」呢種廢話欄位。

點認一個「表」

B. 電郵：一封信入面成疊嘢

一封信入面通常夾住四五份文件。部機會將信本身讀一次， 然後將每一個附件當成一份新文件，由頭再行一次成條流水線。

不過信尾嗰啲公司 logo 細圖唔算文件，會跳過—— 唔係就要為咗讀一個信頭而落載 30 MB 嘅 OCR 模型。

  • .msg 用 msgreader、.eml 用 postal-mime、 .mht/.mhtml 當 MIME-HTML 網頁封存去拆。
  • 信嘅表頭同內文係分開兩個 block 交去搵欄位嘅。 唔分開嘅話，「Date:」會將成篇內文吞埋做佢個值 （因為續行只會喺同一個 block 入面發生）。
  • 附件多過 10 個就先出一句警告。

點分「文件」同「排版裝飾」

Outlook 出簽名檔 logo 嗰陣，會用 image001.png、oledata.mso、logo1.jpg 呢類自動命名。 人手夾嘅嘢從來唔會咁——IMG_1234.jpg、 chop.jpg、Signed scan.pdf 全部唔中。

所以條規則係「符合呢個命名 + 細過 200 KB」， 另外 related 或者有 contentId 嘅一律當裝飾。

特登唔睇 Content-Disposition。 Outlook 將簽名 logo 導出成 Content-Disposition: attachment 而且完全冇 Content-ID——任何靠 disposition 嘅規則， 喺呢度會啱啱好讀反。

被判定為裝飾嘅嘢：唔解析、唔入 pages[]、 唔出「=== Attachment: image.png ===」段落、唔出任何欄位去污染跨文件比對。 但係個 blob 保留——因為有人真係會將公司印直接貼落信入面， UI 亦留咗個「+ N inline images」展開位。

原始 bytes 有保留上限：單檔 25 MB、全部合共 80 MB。 超過就照解析文字，只係唔留原檔—— 一個有 size 但冇 blob 嘅文件，就係 viewer 用嚟講「呢個下載唔到」嘅訊號。

OverviewA nine-step pipeline

Start to finish, not one step says "ask AI to look at it." Every step is a hand-written rule, and every rule can be traced back to a line of code and the reason it was written that way.

Picture a stack of paper you can't read. You need to do nine things:

Work out what kind of paper it is → read the letters on it → remember where each letter sat → tell which bit is a paragraph and which is a table → find "name: answer" pairs → fix names that got misread → compare against a tidier copy sitting alongside it → check with your eyes whether anyone signed or stamped it → finally copy it all into one tidy table.

The one thing to understand first: a PDF has no such thing as a "field." A PDF only remembers "this string of characters is drawn at x=72, y=708, in 10pt type." To a computer, "Contract Number" and "C159040" are just two piles of letters each drawn at some coordinate — nothing connects them.

So step ③ is the most important thing on the whole line: from a pile of coordinates, rebuild "these two piles of text are the same line," "this line has three cells," "these three cells line up with the three cells in the row above, so together they're a table." Everything after this step is built on top of that reconstructed layout.

①Identify the file extFor · parseByExt Tier 0

Like a mail carrier: pick up the parcel, first work out whether it's a letter, a photo, or a book, then put it in the right bin — because different things need different ways to open.

The first step isn't reading content, it's deciding which route to read it by. The order of decision is fixed:

  1. Filename wins first. If the filename ends with an extension (1–8 alphanumeric characters), that's used, MIME is never consulted.
  2. MIME type is only checked when the filename has no extension at all.

Why does the filename win? Because senders mislabel constantly — the demo email carries a .mht attachment typed application/octet-stream. The filename is what both the sender and the user actually see.

The MIME fallback also covers a real bug: when PostalMime meets an attachment with no filename it hands out a placeholder like attachment_3, whose trailing dot is the whole "extension."

Once identified, there are five routes:

  • PDF → check for a text layer; present, read it directly, absent, fall through to OCR automatically.
  • Image (png / jpg / gif / bmp / tiff / webp) → always OCR.
  • Excel / CSV → read directly, no OCR at all — already structured data.
  • Email (.msg / .eml / .mht) → read the message itself, then recurse the whole pipeline over every attachment.
  • Anything else → says plainly "unsupported," never pretends to have read it.

Attachments inside an email re-enter this same decision tree (depth + 1), so a PDF, image, or Excel file inside an email is read the same way.

But containers do not nest.

.msg and .eml only unpack at depth 0 (the file the user picked themselves); .mht is relaxed to depth ≤1 (it can sit inside an email, but not one level deeper than that).

So an email carrying another .eml inside it — the inner one is never unpacked. It's reported as "unsupported, skipped," though the file itself is still there and downloadable.

This is deliberate: if containers refuse to nest, unbounded recursion is impossible. The cost is that a forwarded email needs one manual layer of unwrapping; what's bought back is that no malicious or corrupted .eml can ever hang the tab.

Functions

  • extFor(fileName, mimeType) — line 2872. Extension first, falls back to MIME_EXT (line 2847) when unrecognized.
  • previewKindFor(ext) — line 2882. Decides which viewer the App uses to display it.
  • parseByExt(file, ext, notify, depth, deadline) — the actual dispatcher. deadline is passed down by the caller, so one attachment using up all its time doesn't hang the whole email.
  • parseFile(file, onStatus) — line 3682, the sole public entry point. Besides the parse result, it also attaches a result.self (line 3693), describing the user's own chosen file in the exact same shape as an attachment, so the viewer can treat them uniformly.

Time budgets

The whole engine runs on the browser's main thread, so every step has to know when to let go:

  • Soft deadline ATTACHMENT_OCR_BUDGET_MS = 420000 (7 min) — the ceiling for OCR. On expiry it stops at the current page, keeping everything read so far, and marks truncated: true. This is what actually governs how long an attachment gets.
  • Hard timeout ATTACHMENT_TIMEOUT_MS = soft deadline + 150000 (9.5 min) — withTimeout rejects outright, throwing away everything read so far. This guards against one corrupt PDF that never resolves, hanging every attachment behind it.
  • withTimeout(promise, ms) line 2918, yieldToUi() line 2932 — the latter is one await, purely so the browser gets a beat to repaint; without it the tab looks frozen for the whole email.
  • MANY_ATTACHMENTS_THRESHOLD = 10 line 2893 — above this a "⚠ N attachments found, this may take a while" notice fires first. Purely informational — nothing is blocked or capped.

The 150 seconds between the two deadlines isn't an arbitrary pad — it's "one slow page's worth."

The soft deadline is only checked between pages, so whichever page is in flight when it expires has to finish regardless. If that overrun crosses the hard timeout, the partial result the soft deadline exists to preserve gets thrown away anyway — the soft deadline would have been for nothing.

So the gap has to be wide enough for the slowest single page to finish: a full-page A4 scan takes the better part of two minutes on a laptop.

Worth noting: the hard timeout used to be 45 seconds, and it dropped a real signed agreement entirely — OCR legitimately needs a minute or two.

Attachments fetch bytes first, then parse, and fetching bytes happens outside withTimeout (the comment near line 3048 says so plainly). Decoding is fast; parsing is what hangs. With this ordering, even a PDF that never finishes rendering leaves the user able to view and download the attachment in the App.

⑤Finding fields: "Label: value" parseLinePairs · extractFieldsFromBlocks Tier 2

Like filling in a form: the left side writes "Name:", the right side writes the answer. The machine goes line by line looking for "things with a colon" — before the colon is the question, after it is the answer.

Real documents aren't that obedient though, so a few more tricks are needed.

How many pairs can one line hold?

Forms routinely put two pairs on one line. So the first thing is to split a line back into cells using "two or more spaces" (that whitespace is the layout trace left behind by step ③), then look cell by cell.

Four written shapes are recognized:

  1. Colon in its own cell: ["To", ":", "Brightway Ltd"]
  2. Colon stuck to the front of the value cell: ["To", ": Brightway Ltd"]
  3. Colon stuck to the back of the label: ["To:", "Brightway Ltd"]
  4. The whole pair in one cell: ["To: Brightway Ltd"]

What counts as a "label" at all?

  • No longer than 45 characters
  • Can't be purely digits, currency symbols, or brackets ($1,234.00 is not a label)
  • Can't start with http
  • First character must be a letter, digit, Chinese character, or an opening bracket (forms genuinely write it this way: (Min)Contract Start Date:)
  • Word count: max 6 words with no colon; max 9 words with a colon

Why can a punctuated label run longer? Without a colon, "looks like a label" is the only evidence there is, and past six words ordinary sentences start slipping in. But an explicit colon is already strong evidence on its own — "Total Direct Variable Cost with HKT (HKD):" is seven words and unmistakably a label at a glance.

What if the value wraps onto the next line?

If a line has only a label and no value (e.g. "Installation Address:", with the address on the next three lines), it's recorded as a dangling label, and the lines that follow are attached as its value.

But the attachment is done cautiously, behind three gates:

  • Stop immediately the moment a following line itself contains a "label: value" pair — a value never contains another pair inside it.
  • If 60% or more of the following lines are "just a short label" (e.g. Approver-5 / Approver-6 / Approver-7 stacked one under another), that's not a value, it's a column of labels, and must not be swallowed.
  • Any line that is itself purely a label cuts off the attachment.

What about pairs separated by column position alone, no colon?

"Project Description　　Maintenance Service for…" — separated purely by column position — is shape-identical to "Proposed New Contract 　　Previous Contract" (a two-column heading). Layout alone gives no way to tell them apart.

So this trick only fires when the left-hand cell is a label the engine already recognizes — recognition supplies the evidence punctuation doesn't.

Two modes

extractFieldsFromBlocks(blocks) (line 187) looks at each block, first counting how many of its own lines already carry pairs:

  • LIST MODE (line 199) — pairLineCount >= 2 and >= ceil(lines.length * 0.4). Each line emits its own pairs; a line with no pair that isn't itself a bare label continues the previous field's value (wrapped addresses etc.).
  • SEQUENTIAL MODE (line 223) — everything else. A bare-label line can swallow the rest of the block as its value, but is gated by the cut at line 243 and looksLikeLabelColumn at lines 245–248 (≥2 lines, 60% of which are ≤2-word bare labels).

⑥Canonicalizing field labels: Equlpment Liat → Equipment List canonicalizeLabel · ocrDistance Tier 2

OCR routinely misreads letters: i looks like l, o looks like c. So the machine keeps a "correct spelling book," and when it sees a word that's close-but-not-quite, it checks the book: "did you mean this one?"

One important rule though — if two entries in the book both look about as close, it would rather not change anything at all. Getting it wrong is worse than not fixing it.

The same document often reaches an email multiple times: a clean PDF, a scanned copy, and an Excel workbook. Each spells its field labels differently. Left unaddressed, the same thing would answer under three different names, and cross-document checking becomes impossible.

Three layers, cheapest first:

  1. Fold first: lower-case, strip everything that isn't a letter, digit, or Chinese character. Email for IPT/PABX and EmallforIPT/PABX differ by only one letter after folding.
  2. Look it up: identical after folding → use the canonical spelling directly. Then check a synonym table (attn → Attention, quotationnumber → Quotation No).
  3. Fuzzy match: compute "how many characters need to change to become identical," closest one wins — but only after clearing three gates.

How is "how many characters" computed?

The standard approach is edit distance: the minimum number of deletions/insertions/substitutions to turn one string into another. But one key twist is added here —

OCR mistakes follow a pattern; they're not random. It confuses i / l / 1 / t with each other, confuses o / c / 0 / e with each other, but it will never read i as z.

So a substitution within the same confusion group costs only 0.3 points; every other substitution still costs 1. That way "Malntenance Perlod" (two OCR-typical errors, 0.6 points total) climbs onto "Maintenance Period," while "Maintenance Charges" (a genuinely different label) doesn't.

Nine confusion groups: il1t · oc0e · as5 · nmh · uv · gq9 · b6 · z2 · fr

Three gates

  1. Too short, doesn't play: fewer than 6 characters after folding gets no fuzzy match at all. At lengths like "To", "Tel", "Date," almost any other short label falls within tolerance, so matching there would be inventing matches, not repairing them.
  2. Too far, doesn't play: distance can't exceed "length × 0.25".
  3. Too close a tie, doesn't play: the runner-up must trail the winner by at least 0.5 points. Two candidates that similar means genuine ambiguity — better left unchanged.

Gate three has a subtlety: the "runner-up" only counts as a rival if it's a different label. The same label reaching this point twice — once from the built-in dictionary, once from a sibling attachment using it — is agreement, not ambiguity; treating that as a tie would reject exactly the clearest matches.

  • Never add a label that is a prefix, suffix, or one-character variant of another. If a document genuinely prints both, leave both out of the table.

⑦Teaching the messy copy from the clean copy in the same email buildCleanVocabulary · reconcileOcrFields Tier 2

A photocopy in your hand is hard to read — but the same envelope has a crisply printed copy of the same thing. So the clean copy becomes a "dictionary" used to check the blurry copy's words.

But digits are never changed. Because "5" or "6" — nobody can know which one was really meant, and guessing would mean writing down a reference number that doesn't actually exist.

A purchase-requisition email almost always carries the same document twice: a clean copy (a PDF with a text layer, or the Excel it was exported from), and a signed scan of it. The scan is the one OCR mangles — and the right answer is sitting right next to it.

What goes into the dictionary

  • Every attachment in the same email that never went through OCR — all of its field labels and values.
  • Every attachment's filename — even if the document inside is a scan, the filename itself is always accurate text.
  • Only words 5 characters or longer containing a Latin letter are collected. Short words collide too easily.

Fields the engine inferred itself (derived, e.g. Signature = Yes (page 3)) are never allowed into the dictionary. Those aren't the document's own words. If they were included, "Signature" and "Not found" would end up rewriting real text in the scan next door.

Repairing values is far more conservative than repairing labels

A label is a name; getting it wrong at worst mispositions one row. A value is data; silently "correcting" a quotation number into a different real number is worse than leaving a visible OCR typo.

So every word must clear five gates before it's changed:

  1. At least 5 characters after key-folding
  2. If the dictionary already has an identical key → don't change it. The letters already agree; only punctuation or case differ, and changing it would be a loss, not a fix.
  3. Distance can't exceed "length × 0.2" (stricter than the label's 0.25)
  4. The runner-up must trail by at least 0.5 points
  5. Never change a digit to a different digit — the digits on both sides are extracted and compared; any mismatch stops the repair immediately

Case follows the scan's own authority

OCR never gets case wrong on its own (it reads MAINTENANCE as MAlNTENANCE, never as maintenance), so the scan's own casing is the authority, and the dictionary side's case is discarded.

But this only applies to purely alphabetic words. An email address, a reference number, a part number's casing is part of the string itself, not something determined by its position in a sentence — those use the dictionary's exact spelling directly; re-casing them would be damage.

C. Sideways and upside-down scans

When a book is held crooked, you tilt your head to read it. The machine does the same thing — except it "tilts four times and keeps whichever reads clearest."

Scanned documents are routinely sideways or upside down. The approach:

  1. First try reading a shrunk-down version (long edge 1000 px) — fast and cheap.
  2. If the average confidence is below 0.7, retry in order 180° → 90° → 270°. 180° goes first because it's both the most common mistake and the cheapest to rule out.
  3. Comparing the four orientations is not done by confidence alone, but by a score: confidence × √(characters recognized).
  4. Orientation is decided once per document, then reused directly for the following dozens of pages — never re-tried four times per page.

③Rebuilding layout: coordinates back into "lines / cells / columns" groupItemsIntoLines · lineItemsToCellsAndText · clusterColumnStarts Tier 3

Imagine a whole page of text got shredded into scraps, each scrap with a note on the back saying "I was originally 7 cm from the left, 3 cm from the top." What you have to do: group scraps at similar height into one line → within a line, split apart scraps that sit far apart into separate cells → then check whether each line's cells all line up at the same few positions — if they do, that's a table.

This step has four moves, each doing one small thing on its own, but get one wrong and the whole page falls apart.

1 · Which fragments are on the same line

Y-coordinates within 2.5 points of each other count as the same line. Tolerance is used rather than exact equality because different font sizes on the same line have slightly different baselines.

Then the page's median line spacing is computed. If a line's gap from the one above exceeds "median × 1.7" or "median + 6" (whichever is larger), it's flagged bigGapBefore — meaning "a new chunk starts here."

The median is capped at 20. On a page with only a few lines, the median can balloon, which would glue "heading + table + totals" — three completely different things — into one lump.

2 · How a line is split into cells

Scanning left to right, whenever the gap between two pieces of text exceeds "10 points" or "font size × 2" (whichever is larger), an invisible column boundary is assumed there, splitting into two cells.

Once split, each cell records three things: the text inside it, the x it starts at, and each individual fragment's own x inside it. The third seems redundant, but saves the day later — see "two columns touching" below.

3 · Which x-positions are really the same column

All cell starting-x values across the whole region are pooled together, clustered within 22 points of each other, and each cluster's average taken. Those averages become that region's "invisible column lines."

A document never states how many columns it has — that's clustered out of many lines' starting positions themselves.

4 · A row wrapped into two lines, rejoined

Narrow table columns wrap their content onto the next line. The condition for detecting this is strict:

  • The whole region must show two clearly distinct spacing scales (a tight wrap-gap, a looser row-gap). If every gap is identical, every line is its own row — merging must not fire.
  • The line below's gap must fall within "tightest gap × 1.25."
  • Every cell in the line below must land on a column the row above already has (±14).
  • And the line below may only touch one column. Touching two or more means it's a new row, not a wrap — otherwise several consecutive table rows at tight spacing would keep gluing together into one blob.

A line reading "To：ABC Company 　　Date：2026-02-02" — without preserving this trace — would let the second pair leak into the first pair's value, becoming To = "ABC Company Date：2026-02-02".

In other words: layout information isn't lost, it's encoded as whitespace, carried forward for later steps to use.

④Sectioning: is this a paragraph, or a table? buildBlocks · rejoinTableSections · classifySection Tier 3

Looking at a page, you instantly know which bit is "a paragraph" and which bit is "a table" — no thinking required. The machine has no eyes; all it can do is count: "are there several lines all starting at the same few positions?" Yes → treat it as a table; no → treat it as a paragraph.

A page is first split at "big gaps" into chunks (sections), then each chunk is judged individually. The order of decision:

  1. Fewer than 2 lines have more than one cell → paragraph. If not even two lines line up, there's nothing to call a column.
  2. Half or more of the lines are themselves "label: value" pairs → paragraph. Forcing this one-pair-per-line shape into columns would split every label from its own value — and step ⑤ already knows how to handle this shape directly.
  3. 3 or more column lines exist, and
    • at least 3 of them are "strong columns" (used by 2 or more lines), and
    • at least 2 lines are "wide rows" (cell count in that line ≥ column count − 1)
    → table.
  4. If there are 3 strong columns but not 2 wide rows, there's one more fallback: "an uneven table" — e.g. a Remarks column wraps across many more lines than the rest, so no single line spans "most" columns. Here, "where a new row starts" is counted instead: a line touching both the first column and at least two other columns starts a new row. At least 2 such starts are required to count.
  5. Otherwise → paragraph.

Why all this trouble, rather than "see columns, call it a table"?

Because a table and a form look identical, yet need to be read by exactly opposite methods.

"Customer Number｜10029384｜Customer Name｜GREEN VALLEY HOSPITAL" — this is four fields, not a table meant to be displayed intact.

But "File Name｜Uploaded By｜Upload Date" followed by eight rows — this is data, meant to be shown as a table exactly as-is, never flattened into fields (otherwise nonsense fields like FILE NAME = UPLOADER would appear).

The only way to tell the two apart is by shape — which is why so many conditions are needed up front.

A table got cut apart by row spacing — how is it rejoined?

In a wide table, the gap between rows can be larger than the gap of a wrapped line within one row — e.g. 21pt between items, 12pt for a wrap within one item. As a result every item got treated as "a new chunk," and everything after the first item fell out of the table into loose paragraphs.

The fix isn't loosening the "big gap" threshold (that would break other things) — it's asking one more question: "are the columns in the chunk below all columns the chunk above already has?"

If so, rejoin them. Four conditions, all required:

  • Both chunks must have at least one line with 3 or more cells (a caption doesn't share columns with the table below it)
  • The lower chunk's first line must have gapRatio no greater than 2.2 — a genuine change of subject leaves far more white space, and no amount of column alignment should rejoin it
  • The lower chunk must have at least 3 column lines
  • Every column line in the lower chunk must match one in the upper chunk (±14). Not "most" — every one.

The first version of continuesTable was "at least 3 shared columns + 60% overlap," and the result was a whole page gluing together into one table. The fix required "every column below must match one above," plus REJOIN_MAX_GAP_RATIO before the bleeding stopped.

The lesson, recorded in Docparse/CLAUDE.md: a loose structural test, applied across a section boundary, will always find a way to say yes.

⑧Reading ink: signatures and company chops analyzeInkImage · findSignatures · findChops Tier 1

A signed contract and an unsigned one have identical text. So no amount of good reading can tell them apart.

The only difference is handwritten ink. So this step stops reading characters and just looks at the picture:

Signature = one big, long stroke, mostly empty inside, far larger than the text around it.
Chop = a closed ring, usually red or blue, trapping text inside it.

Three observations carry the whole detector:

  1. Printed text is thousands of small, very uniformly sized ink blobs.
  2. A signature is one sprawling stroke, several times bigger than any printed character, and critically empty inside its own bounding box.
  3. A chop is coloured, and on a business document almost nothing else is.

1 · First work out what counts as "white paper"

You can't assume white = 255. A grey photocopy's "white" might only be 0.75. So the page's brightness distribution is counted first, taking the 90th percentile as "paper" — a high percentile rather than the brightest pixel, because a single white speck or a blown-out highlight would otherwise throw the whole reference off.

Then: darker than "paper × 0.78" counts as ink.

2 · Split into two layers

  • Dark layer — every sufficiently dark pixel. Signatures live here.
  • Colour layer — pixels with saturation ≥ 0.30. Chops live here. The threshold can't be too low, or JPEG colour fringing around black text would count as colour.

Red band: hue ≤25° or ≥315°. Blue band: 195°–315°. Green and yellow are deliberately excluded — those are highlighter and letterhead artwork.

The red band deliberately reaches back to 315° so that magenta counts as "warm" too. A letterhead's magenta logo is otherwise the one piece of artwork on the page shaped enough like handwriting to be mistaken for it, and leaving a gap between the two bands would let it slip through as "colourless."

3 · Merge connected dots into blobs (connected components)

Starting from one point, flood outward in eight directions, sweeping up every connected ink pixel — like the bucket-fill tool in a paint program. Each blob has six measurements taken:

4 · Recognizing a signature

First find fragments that "already don't look like print": taller than 1.6× glyph height, not too solid. Then merge them back into a group — a signature is rarely one unbroken stroke; lifting the pen once, or scan resolution breaking a thin stroke apart, turns "Cherie Wong" into four separate blobs.

Merge condition: horizontally close (≤ glyph height × 2), and vertically must overlap. "Horizontally close" alone would let a logo glue to the heading below it, becoming "one very irregular gesture."

Once merged, a group must clear nine gates to count as a signature:

  1. Height ≥ glyph height × 2.2, width ≥ glyph width × 5
  2. Aspect ratio between 1.2 – 14 (a signature runs along the line, not down it)
  3. Can't be wider than 75% of the page or taller than 30% of the page (that would be a rule line or a border)
  4. fill ≤ 0.40, solidity ≤ 0.55
  5. ruleRatio ≤ 0.30
  6. Can't look like printed text (see below)
  7. Can't sit on top of positions the PDF itself says are typed text (see below)
  8. Can't be dominated by warm colour (>50% red pixels and more red than blue) — a pen never does this

How is "printed text" recognized? — by the baseline.

Printed characters all sit on the same baseline and are all about the same size; handwriting does neither. So: a group of 6 or more pieces, where the baseline standard deviation ≤ group height × 0.16 and the height standard deviation ≤ mean height × 0.28 — that's printed text (in practice, a large heading, since only a large heading is big enough to reach the size gates above in the first place).

Why 6 and not 4? Because a genuine signature broken into four or five strokes can, by chance, land regular enough to look printed — and two of the signed documents here are exactly that. A printed heading always has more letters than that.

What the PDF itself says beats any heuristic.

A PDF with a text layer already states, precisely, where every typed character sits. Ink sitting on top of those positions is print, by the document's own account — no guessing needed.

This is exactly why the printed words "Authorised Signature" under an empty signature line on an unsigned quotation are never reported as a signature.

Method: text positions are drawn onto an 8×8-pixel coarse grid; a blob where more than 60% of its cells are text cells gets excluded. A scan has no text layer, so it can only rely on shape.

5 · Recognizing a company chop

What makes a chop a chop is its outline: a continuous ring, oval, or rounded rectangle enclosing text inside it.

The decisive test is called largestHoleRatio: flood-fill inward from the four edges of the bounding box, and see how much paper can't be reached. Whatever can't be reached is a "hole" trapped by ink.

This is a topological test, not a shape-ratio test — which is why round, oval, and square chops all pass it, and no shape ratio could do this job.

No matter how sprawling a signature gets, you can always walk in from the paper edge; a closed chop, you can't.

Technical detail: paper is flooded 4-connected, ink is 8-connected. Reversed, the background would escape diagonally through a one-pixel-thin stroke, and every ring would read as open.

Remaining gates: short side ≥ the larger of "page long edge × 0.025" and "glyph height × 3.5" (the floor is deliberately low, because a genuine signature chop as small as 40 pixels exists in the corpus); long side ≤ page long edge × 0.35; aspect ratio 0.30–3.2; fill 0.02–0.55 (above that it's a solid logo); solidity ≤ 0.75 (above that it's a solid shape, not an outline); ruleRatio ≤ 0.55 (above that it's a coloured table border); hole ≥ 0.15.

Every blob is asked the question in both layers: the colour layer can cleanly pick up a red chop even where it's stamped over printed text; but a photocopy or grey scan has no colour left at all, and there the chop can only survive in the dark layer.

6 · Don't double-count, and don't be greedy

  • Same-kind marks overlapping more than 0.5 → counted as one.
  • Different-kind marks need 0.85 overlap to count as one — because "a chop stamped over a signature" is the normal way of signing here, and the two naturally overlap. Merging too eagerly would answer "chopped" while losing "signed."
  • A page reports at most 6 marks.
  • If a page finds more than 6 signatures — that's not six signatures, that's a diagram, a map, or a photo. Every signature finding is discarded entirely, only chops are kept. Honestly saying "none" beats reporting noise.

7 · Which pages are worth looking at

Looking at a page means rendering it once and scanning every pixel — expensive. So:

  • Documents ≤8 pages → every page gets looked at.
  • Longer than 8 pages → pick pages whose content mentions signing (one bilingual regex: authorised signature, for and on behalf of, company chop, Chinese equivalents…), plus the last 3 pages, capped at 8 total.
  • The order of inspection is also deliberately arranged: pages mentioning signing go first. Some form templates take several seconds each to render, and the 25-second budget can run out part-way through — inspecting front-to-back would spend the budget on exactly the pages least likely to have a signature.

"Never looked at" and "looked at, found nothing" are two different things, and must never be conflated.

Looked and found nothing → marks = [] → reports Not found.
Never looked → marks stays undefined → never counted as clean.
Some pages unlooked-at → reports Not found on the pages checked.

Even a render failure resolves to resolve(null), not an empty array — an empty array would claim "I looked."

⑨ATQ: one table becomes one record per item parseAtqWorkbook · parseAtqCostTable · dedupeAtqRecords Tier 1

An ATQ is an "Authority to Quote" form. One table on it might cover four different things being bought.

What the people downstream need isn't "one table" — it's four separate little cards, each saying what was bought, how much, and from which vendor.

The catch: the same table often gets sent twice — once as Excel, once printed to PDF. Count both, and four things become eight.

Two routes, one shape

An ATQ can arrive two ways, and the two routes are deliberately made to produce the identical record shape, so nothing downstream ever needs to care which version an email carried:

  • Excel version (parseAtqWorkbook) — only engages when both a Cost and an ATQ sheet are present. Cost has one row per item; ATQ is a single column of "column A = label, column B = value" holding data shared by the whole table (customer name, contract number, start/end dates…), merged into every item.
  • PDF version (parseAtqCostTable) — reads the same columns back out of the printed cost table.

Three hard problems in the PDF version

  1. The header spans three physical rows. Which of the three rows a word lands on shifts depending on how long the text above it ran. So columns can't be identified by position — every row before the first item has to be joined vertically, column by column, before identification.
  2. One item can span several rows. Each column wraps on its own, so the row carrying the item number holds only the first line of every cell, and the rows beneath hold the rest. The only marker is that the item-number cell is empty.
  3. Continuation lines aren't always joined with a space. Checked cell-by-cell against the Excel version of the same ATQ (the only ground truth available), three shapes occur across the corpus: a reference followed by a descriptor, a descriptor broken mid-token, and a work-order list wrapping with its comma leading. Rule: if the break point already carries punctuation (left side ends in -, or right side starts with ,.;:)), don't add a space — this one rule reproduces all three shapes exactly.

Also, a reference number is a token that never breaks. So a reference value shaped "all alphanumerics + spaces" has every space stripped — those spaces were introduced by column wrapping, not part of the content.

The four-key guard. If a table is missing any of itemNo, productType, vendor, totalValueOfQuotation, it's not the cost table, no matter how much it looks like one.

This guard broke once: one ATQ printed Total Direct Variable Cost with HKT (HKD): on the same physical line as the first row of the header. After folding, that whole sentence stuck to the front of ITEM NO. → itemNo went unrecognized → the four keys weren't complete → every item on the whole table vanished.

The fix changed the regex from "anchor at the start only" to "anchor at the start OR the end" (/^itemno|itemno$/) — because text leaking in from above always shows up as a prefix.

When both fire: 8 items vs. 4

This is the single best teaching example in the whole codebase.

atqRecordsFromTables was added so a PDF-printed ATQ would produce the same records as the Excel version. Reasonable.

But every demo email carries both versions at once, and the merge line was records = records.concat(owned). Result: a Cost sheet with only 4 items had the App reporting "this ATQ covers 8 items." The whole corpus went from 12 real items to 32 — and that inflation was reported as a win at the time.

The lesson became rules:

  • Before adding any path that can emit fields or records for a document type an existing path already handles, first write down what happens when both fire, then go find a document in the corpus that triggers both. Here, both firing at once is the normal case, not the edge case.
  • When both can fire, the identity key belongs at the merge point, not in either producer.
  • And — when two sources cover different columns, that doesn't mean the weaker one should win to preserve coverage. Check first whether the authoritative source actually has that data. This time it did: the Cost sheet had all eleven columns all along; it was the then-current COST_COLUMN_MAP (an exact-string map, since replaced by today's regex-based ATQ_COST_COLUMNS) that only read five.

Deduplication rule

  • Identity key = ATQ reference number. First check the record's own ATQ Ref. No. field; failing that, extract it from the source filename using ATQ-\d{6}-\d{5}-V\d{2} (the PDF version doesn't always print the reference as a field, but both attachments are named after it).
  • Within a group sharing one reference number, if any Excel record is present, every PDF record is dropped.
  • Records whose ATQ can't be identified are always kept, from either side.

Why does Excel win? Because it's the export source — exact values, no OCR, no layout inference. Also: when one request covers only some of an ATQ's items, the Excel file is already narrowed to those ("(Item 2).xlsx" against a fully approved PDF of the whole form) — taking the PDF would add items this requisition was never for.

Why aren't unidentifiable records dropped? Because a duplicate is a nuisance a person can see at a glance; a silently dropped item is a wrong purchase requisition.

Matching a quotation reference back to its attachment

Each item's Quotation field carries a quotation reference number. Usually one attachment in the same email is that quotation, named after that number.

  1. First try "filename starts with this reference."
  2. No match, relax to "reference appears anywhere in the filename" — so Signed_QT-2600008.pdf still resolves.
  3. Both passes require the reference to be followed by a non-alphanumeric boundary, otherwise a truncated reference would match a longer one (QT-260 matching inside QT-2600008).
  4. If the cell reads "reference - description" (e.g. QT-2600008 - hardware), the head is cut off and retried — but the head must still look like a reference (≥5 characters, no spaces, at least one digit), otherwise "Maintenance - 2026" would degrade into searching for "Maintenance."
  5. More than one file can match (an original plus a signed copy).
  6. No match: explicitly writes (no matching attachment).

⑩Excel, email, and attachments processExcel · processEmailAttachments Tier 1 Tier 0

A. Spreadsheets: already structured data

Excel doesn't need character recognition — every cell already says plainly where it is. So OCR never even opens.

The question isn't "how to read it," it's "which cells are a filled-in form, and which are a list."

Without that judgment, a data table's header row produces nonsense fields like "Product Number = Product Description."

Recognizing a "table"

A row with 4 or more filled cells, joined by at least 3 consecutive rows that are just as wide and land on at least 3 of the same columns — that whole run is a table, skipped entirely, no fields extracted.

How the remaining rows are paired

Any cell that looks like a label is paired with the next non-empty cell to its right as the value.

One exception: if the "value" itself also looks like a label, and there are two or more further cells behind it, it's a section heading sitting in front of a form row (e.g. Quote Info │ Quote Number │ 482022078), and is skipped rather than paired.

Separately, exporting a sheet to CSV dumps out hundreds of empty trailing columns from the "used range," which reads like a wall of commas (easily mistaken for garbled text). So trailing empty cells per row are stripped and fully-blank rows are dropped; interior blank cells stay untouched.

Two consumers, two blast radii.

Docparse/index.html only reads fields, records (including rec.sourceFile), plainText, pages, hadOcr.

PR Assistant App.html reads all of the above, plus attachments[], self, truncated, signing.

So: a change verified only in Docparse is not verified. Docparse never touches attachments or signing at all.

And the App reaches inside the page tree as well: docHeadingLines joins doc.pagesIndex back into pages[], then reads .pages[0].blocks[], taking each block's lines[] to decide — from a document's own first-page heading — whether it's an Agreement, a Quotation, or an ATQ.

blocks[].lines is a consumed key, not an internal detail.

records uses || undefined rather than [] (line 2826) — because "this document isn't an ATQ" and "this ATQ has zero items" are two different facts.

⑫Where it can go wrong, and how it's verified

This is a very hard-working assistant, not an infallible machine. What it does is help you gather everything and point out where things don't match — the final call is still a person's.

Known failure modes

SituationWhat happensWhy it isn't "fixed"
A signature typeset in a script fontReported as Not found For "did anyone sign this by hand," this is the honest answer
Quotation attachment gets renamed(no matching attachment) Matching is filename-only; the quotation is never opened — the price of being fast and cheap
OCR misreads a digit inside a reference numberDisplayed exactly as misread "Correcting" it into a different real reference number is worse than leaving a visible typo
Very long scanned documenttruncated: true, later pages unread Stopping at the current page and keeping what's read beats losing the whole attachment
Unusual form layoutFields missing, or junk fields appear Loosening the heuristic breaks every other document — see every ⚠ above
PDF with no text layer at all, too blurryOCR returns confident-looking nonsense OCR never hands back a blank page — it hands back plausible-looking garbage, so what's checked is the confidence score, not "did it return something"

"Detected fields" is a heuristic, not AI, and definitely not verified.

Product copy must never present it as a validated result. Signature and Company Chop need even more care — they're the result of reading pixels, a finding for a human to confirm, never a substitute for looking at the page.

The four-rung verification ladder

RungTimeWhat it does
Rung 0Seconds Plain Node. The engine uses globalThis rather than window (deliberate, see the last line of the file), so require('./docparse-engine.js') gets canonicalizeLabel, canonicalizeFields, reconcileOcrFields, extractFieldsFromBlocks, fieldsFromTable, parseAtqCostTable, analyzeInkImage, and more — no library needs to load. Rung 1A minute _atqprobe.html?f=<file> against a single extracted attachment; must run over HTTP, not file://
Rung 220–30 minutes _regress.html against the seven demo emails, A/B'd against a baseline engine, diffed per attachment into LOST / GAINED / CHANGED

Tier 3 and Tier 2 always require rung 2; Tier 1 requires rung 1; Tier 0 requires grepping both consumers for every key touched. A full A/B costs half an hour, so batch fixes together into one run — and re-run it after the last edit, because the run that validated fix #1 says nothing about fix #4.

Decompose deltas, or don't report them.

"Records rose from 11 to 32" was once reported as a win, when the corpus actually held 12 real items and the rise was the same ATQ counted twice.

A single count delta is not a result. Break it into new / duplicated / reclassified / lost, name the document behind each component, and put lost first — a change that gains 20 fields and loses 1 real one is usually a bad change. If any component can't be accounted for, say so plainly rather than rounding it into the win.
